# Claude Code로 데이터 분석 자동화 파이프라인 만들기

> Titanic 캐글 프로젝트를 예시로, Claude Code와 협업하여 재사용 가능한 스킬 체계를 구축한 과정

## 이 문서의 목적

Claude Code를 처음 접하는 사람이 "아, 이렇게 쓰는 거구나"를 느낄 수 있도록, 실제 작업 세션의 흐름을 기록한다. 단순히 "Claude에게 시키면 된다"가 아니라, **사용자가 방향을 잡고 → AI가 실행하고 → 사용자가 검증하고 → 합의된 내용을 스킬로 저장하는** 협업 패턴을 보여준다.

---

## Step 0: 프로젝트 구조 파악시키기

Claude Code를 프로젝트에 처음 투입할 때 가장 먼저 할 일은 **프로젝트 구조를 이해시키는 것**이다.

### 무엇을 했나

- `CLAUDE.md`에 프로젝트 개요, 디렉토리 구조, 실행 명령어, 아키텍처 패턴, 코드 스타일, 브랜치 전략을 정리
- Claude Code는 대화 시작 시 이 파일을 자동으로 읽어 컨텍스트를 확보

### 왜 중요한가

`CLAUDE.md`가 없으면 Claude는 매번 "이 프로젝트가 뭔가요?"부터 시작한다. 이 파일이 있으면 대화 첫 마디부터 프로젝트 맥락을 공유한 상태로 시작할 수 있다.

### 이 프로젝트의 CLAUDE.md에 담긴 것

```
- Component-Pipeline 패턴 (base 추상 클래스 → 프로젝트별 상속)
- uv 기반 의존성 관리, pytest 테스트
- 브랜치 전략: proj/* (캐글), dev (기능), main (안정)
- 자동화 파이프라인 로드맵 (browse → insight → metric → ... → autopilot)
- 스킬 트리거 테이블 (키워드 → 스킬 매핑)
```

## Step 1: 목표와 TODO 설정

### 사용자의 첫 요청

> "타이타닉 데이터에 대한 인사이트 뽑아봐"

Claude는 `CLAUDE.md`의 스킬 트리거를 읽고 `/kaggle-insight` 스킬을 자동 호출했다. 프로파일링을 실행하고 품질 이슈를 보고한 뒤, 전처리 계획을 제안했다.

### 사용자가 TODO를 직접 정의

Claude의 보고를 본 뒤, 사용자는 구체적인 검증 항목을 직접 지정했다:

> "작업 전에 내 요구사항을 바탕으로 이후 작업을 진행해.
> 1. Fare의 분포를 보여줘
> 2. Cabin을 결측 여부 피처로 변환하는 건에 대한 근거를 대봐
> 3. Sex 값으로 survived를 결정하는 모델을 베이스 모델로 설정
> 4. SibSp/Parch는 가족 크기로 합산해
> 5. Fare=0인 케이스에서 어떤 패턴이 나타나는지 확인해
>
> 하나씩 TODO 목록으로 잡아두고 나와 논의 후 해소가 되었다면 넘어가는 식으로 진행."

**핵심 패턴: 사용자가 큰 방향과 체크리스트를 정하고, Claude가 하나씩 실행하며 합의를 구한다.**

---

## Step 2: 한 단계씩 함께 작업하기

### 패턴 A: 데이터 근거로 논의

각 TODO 항목마다 Claude가 데이터 분석을 수행하고, 사용자가 결과를 검토한 뒤 확정하는 흐름.

**예: Fare 분포 (TODO 1)**
- Claude: log1p 변환 전후 비교 (skewness 4.79 → 0.39)
- 사용자: "log 변환 후의 분포 보여줘" → Claude가 상세 분석 추가
- 사용자: "확정하고 다음 작업" → 다음 TODO로 이동

**예: Cabin 결측 피처 (TODO 2)**
- Claude: HasCabin과 Survived의 관계 분석 (30% vs 67% 생존율)
- Claude: "Pclass와 강하게 교란됨"이라고 보고
- 사용자: **"교란된다는 표현은 비통계친화적이야. 상관성이 높다로 바꿔봐"**
- Claude: 표현 수정 + Pclass 통제 후에도 추가 분별력 있음을 수치로 확인

**핵심 패턴: 사용자는 결론뿐 아니라 표현과 설명 방식까지 피드백한다. 이 피드백은 메모리에 저장되어 이후 대화에도 적용된다.**

### 패턴 B: 사용자가 AI의 빠진 부분을 짚기

**예: 교차 검증 누락**
- Claude가 베이스라인 성능을 보고
- 사용자: **"학습 데이터와 테스트 데이터를 나눴어?"**
- Claude: "아니요, train.csv 전체에 대해 측정한 값입니다"
- → 베이스라인 스킬에 StratifiedKFold 교차 검증 추가

**예: 모델 선정 이유 부재**
- Claude가 LogisticRegression과 RandomForest 결과를 보고
- 사용자: **"각 모델의 형태와 선정 이유를 설명해줘야지"**
- Claude: 선형 모델(해석 가능성) + 비선형 모델(상호작용 포착) 원칙 설명

**예: 피처 설계 검증 부재**
- Claude가 새 피처 4개를 추가하고 모델을 돌림
- 사용자: **"새 피처 정의 및 기존 피처 정의 등 이번 수정사항 다른 모든 것들에 대해서도 충분히 설명되었는지 살펴봐"**
- Claude가 자체 점검: Pclass_Sex 수치 인코딩 오류, FamilySize 중복, IsAloneFemale3rd 과적합 위험 등 5개 문제 발견
- → 스킬에 피처 설계 검증 체크리스트 추가

**핵심 패턴: AI는 실수한다. 사용자가 "왜?"를 물으면 AI가 스스로 문제를 찾고, 그 검증 과정을 스킬에 규칙으로 추가하여 같은 실수를 반복하지 않게 한다.**

### 패턴 C: 실험 결과를 어디에 기록하는가

- 사용자: **"개별 실험은 어디에 기록하고 있는지?"**
- Claude: "기록하고 있지 않았습니다"
- → `outputs/solve/iteration_N/` 구조 설계, 소급 저장
- → .gitignore 수정하여 JSON 결과를 git 추적 대상에 포함

**핵심 패턴: 실험의 재현성과 추적 가능성도 사용자가 챙겨야 한다. AI는 "지금 돌아가는 것"에 집중하기 쉽다.**

## Step 3: 합의된 내용을 스킬로 저장

이 세션의 가장 중요한 패턴: **수동으로 검증한 작업 흐름을 스킬(.md)로 정의하여, 다음에는 자동으로 실행할 수 있게 만든다.**

### 흐름

```
수동 실행 (사용자와 논의) → 검증 → 스킬 정의 → 다음 프로젝트에서 자동 실행
```

### 실제 과정

1. **insight**: 타이타닉에서 수동으로 프로파일링 + 전처리 논의 → `/kaggle-insight` 스킬로 정리
2. **metric**: 타이타닉에서 F1 선정 논의 → `/kaggle-metric` 스킬로 정리
3. **baseline**: 타이타닉에서 Sex 규칙 + CV 검증 → `/kaggle-baseline` 스킬로 정리
4. **solve**: 타이타닉에서 모델 학습 + 피처 인사이트 → `/kaggle-solve` 스킬로 정리
5. **evaluate**: 타이타닉에서 오분류 분석 + 개선 방향 → `/kaggle-evaluate` 스킬로 정리
6. **autopilot**: 위 스킬들을 순차 호출하는 오케스트레이션 → `/kaggle-autopilot` 스킬로 정리

### 스킬 정의 시 사용자의 개입

스킬은 Claude가 초안을 쓰지만, 사용자가 범위와 원칙을 결정한다:

> 사용자: "3번(사용자 확인) 대신 전처리 계획이 둘 이상이라면 개별 브랜치로 파서 진행하고 결과물을 확인한 후의 최선의 것을 남기도록 하자"

> 사용자: "오분류 대상에 대한 패턴을 포착해서 새 피처를 정의하거나 기존 피처를 조정하고, 사용한 모델에 대한 비교분석과 함께 XGBoost와 같은 새로운 모델 사용에 대해서도 검토하는 등의 작업이 추가되면 좋겠어"

> 사용자: "소폭 하락된 것은 아쉽지만, 가능성이 보이는 근거를 바탕으로 한 논리적인 시도 방법이 있다면 시도하도록 스킬에 명시해 (통계적 기법, 수학적 기법, 확률적 기법, 최신의 연구 방법론 등을 고려)"

**핵심 패턴: 스킬은 "이번에 한 것"의 기록이 아니라 "다음에 어떻게 할 것인가"의 정의다. 사용자가 미래 방향을 제시하면 Claude가 스킬에 반영한다.**

---

## Step 4: 피드백을 시스템에 반영

사용자의 피드백은 세 가지 경로로 지속된다:

### 1) 스킬에 규칙으로 추가

검증 과정에서 발견한 문제를 스킬의 Rules/Workflow에 명시:
- "피처 적용 전 검증: 인코딩 방식, 정보 중복, 샘플 충분성, 구간 경계 확인"
- "성능 하락 시 ablation으로 원인 분석"
- "모델 선정 이유를 이전 evaluate의 구체적 한계와 연결"

### 2) 메모리에 선호도 저장

대화 간 지속되는 사용자 선호:
- "인사이트는 데이터 수치 근거에서만 도출, 사전 지식 사용 금지"
- "해석 가능 모델의 계수/중요도를 인사이트로 추출하여 이후 작업에 활용"
- "최종 방향: 사용자 논의 제거, 자율 브랜치 분기 실험, metric 기반 최선 선택"

### 3) CLAUDE.md에 프로젝트 규칙 반영

스킬 현황 테이블, 트리거 매핑, 개발 방침 등이 업데이트되어 다음 세션에서 Claude가 바로 참조 가능.

---

## Step 5: solve↔evaluate 루프 검증

스킬을 정의한 뒤, 실제로 루프가 돌아가는지 검증했다:

```
solve iter1 (LR+RF, 8피처)       → F1=0.7649 (RF)
  ↓ evaluate 1차: 오분류 분석
solve iter2 (피처 설계 오류)       → discarded
solve iter3 (수정 14피처, GB 추가) → F1=0.7706 (GB)  ← 최고
  ↓ evaluate 2차: 수렴 판단
solve iter4 (앙상블 실험)          → F1=0.7691 (앙상블 < GB 단독)
  ↓ 수렴 확정
```

### 이 과정에서 발견한 것들

| 발견 | 대응 |
|------|------|
| Pclass_Sex를 수치 인코딩하면 의미 없는 순서 부여 | 원핫으로 수정 + 스킬에 검증 체크리스트 추가 |
| FamilySize와 FamilyGroup 동시 사용 시 RF 성능 하락 | 중복 피처 제거 규칙 추가 |
| IsAloneFemale3rd (60명, 6.7%)는 과적합 유발 | ablation으로 확인 후 제외, 5% 기준 규칙 추가 |
| 1등석 남성 오분류율 38.5%가 4회 반복에도 불변 | 현재 피처로는 한계 → 수렴 판단 근거 |

## 최종 산출물

### 스킬 7개 (전체 파이프라인)

```
/kaggle-browse    → 데이터 검색/다운로드
/kaggle-insight   → 프로파일링 + 전처리 계획
/kaggle-metric    → 타겟/평가지표 정의
/kaggle-baseline  → 베이스라인 모델 + CV
/kaggle-solve     → 전처리 + 모델 학습 + 인사이트
/kaggle-evaluate  → 오분류 분석 + 개선 방향
/kaggle-autopilot → 전체 파이프라인 자동 실행
```

### 실험 결과 (git 추적)

```
outputs/
├── profiling/     → 프로파일링 요약 + 전처리 계획 JSON
├── metric/        → 평가지표 정의 + 베이스라인 + 피처 인사이트
├── solve/         → iteration별 모델 결과 + ablation
│   ├── iteration_1~4/
│   └── best/
└── evaluate/      → 오분류 분석 + 수렴 판단
```

### 성능

| 모델 | F1 Score | baseline 대비 |
|------|----------|--------------|
| Sex 규칙 (baseline) | 0.7093 | — |
| RandomForest (iter1) | 0.7649 | +0.056 |
| **GradientBoosting (iter3)** | **0.7706** | **+0.061** |

## 교훈: Claude Code를 잘 쓰려면

### 1. 구조를 먼저 잡아줘라

`CLAUDE.md`에 프로젝트 맥락을 정리하면, 매 대화마다 컨텍스트 설정에 시간을 쓰지 않는다. 스킬 트리거를 정의하면 키워드만으로 적절한 워크플로우가 실행된다.

### 2. 큰 방향은 사용자가, 실행은 AI가

"인사이트 뽑아봐"로 시작하되, 결과를 보고 구체적인 TODO를 직접 정의한다. AI에게 "알아서 해"보다 "이 5개를 하나씩 논의하자"가 훨씬 좋은 결과를 낸다.

### 3. "왜?"를 물어라

AI가 결과를 보여줄 때 "왜 이 모델을 썼어?", "왜 이 인코딩이야?", "검증은 했어?"를 물으면 AI가 스스로 빠진 부분을 찾는다. 이 질문이 없으면 AI는 "일단 돌아가는 것"에 만족한다.

### 4. 실수를 시스템에 반영하라

AI의 실수를 발견하면 그 자리에서 고치는 것으로 끝내지 말고, 스킬의 규칙이나 체크리스트에 추가한다. 같은 실수가 다음 프로젝트에서 반복되지 않게 하는 것이 핵심이다.

### 5. 수동 → 스킬 → 자동화의 단계를 밟아라

처음부터 자동화를 목표로 하되, 첫 프로젝트에서는 사용자와 함께 수동으로 검증한다. 검증된 흐름을 스킬로 저장하고, 스킬이 성숙하면 autopilot으로 묶는다.

### 6. 기록을 남겨라

실험 결과를 JSON으로 저장하고 git에 추적한다. "지난번에 뭘 했더라?"를 AI에게 물을 필요 없이, 파일을 읽으면 된다.
